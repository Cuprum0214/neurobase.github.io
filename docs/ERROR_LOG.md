# ERROR_LOG · 错误记录

> 回答一个问题：**从错误里学到了什么？**
> 只记几个**有学习价值**的错误，不要求记录所有错误；理解错误的过程本身就是学习的一部分。
> 每条固定用五个问题：现象 → 最初的误判 → 真正原因 → 怎么修好 → 学到了什么。
> 来源：Vibe Coding 第二项目 · Part 8 RECORD & ITERATE。

---

## 三份迭代档案的分工

| 文件 | 回答什么问题 | 里面放什么 | 写入时机 |
| --- | --- | --- | --- |
| `DEV_LOG.md` | 每个阶段做了什么 | 完成事项、遇到的问题、下一步 | 每一轮更新后 |
| `DECISIONS.md` | 为什么这样决定 | 重要决定 + 原因 + 当时的取舍 | 出现**选型 / 方案 / 取舍**时 |
| `ERROR_LOG.md`（本文件） | 从错误里学到了什么 | 只记几个有学习价值的错误 | 出现**可复用的教训**时 |

## 记录格式（五个问题）

每条错误固定回答下面五个问题，顺序与用词保持一致：

| 要写的问题 | 含义 |
| --- | --- |
| What happened? | 当时出现了什么现象 |
| What did we first think was wrong? | 一开始我们以为是什么原因 |
| What was the real cause? | 真正的原因是什么 |
| How was it fixed? | 最后是怎么修好的 |
| What did I learn? | 我从中理解了什么 |

落盘模板（标题带日期，编号递增）：

```
### E-编号 · 错误标题（日期）
1. **What happened?**（当时出现了什么现象）

3. **What was the real cause?**（真正的原因是什么）
4. **How was it fixed?**（最后是怎么修好的）
5. **What did I learn?**（我从中理解了什么）
```

## 维护约定（硬性）

1. **不是所有错误都记**：只记"换一个项目还会再犯"或"暴露了方法缺陷"的错误；纯手滑、一次性的拼写错误不记。
2. 必须写全五个问题；第 2 问不能省略——**误判方向本身就是最有价值的部分**。
3. 新条目追加在文件末尾，编号递增，**不得跳号或复用**；同日可多条。
4. 每条在索引表补一行「一句话教训」；能对应到某轮迭代的，在 `DEV_LOG.md` 条目里引用编号。
5. 错误被修复后**不要删除记录**：只留"最后能跑"的版本，等于丢掉整个成长过程。

### E-002 · 文档子目录在开发服务器下 404（2026-10-10）
1. **What happened?** 新增「项目文档」功能后，`/docs/PLAN.md` 能正常打开，但 `/docs/schema/term.schema.json`、`/docs/archive/PLAN.v10.static.md` 等**子目录**文件却返回首页 HTML，看起来像"页面不存在"，而磁盘上这些文件确实存在。

### E-003 · 写入封装漏传参数，4 个核心文档被写坏成 4 字节（2026-10-10）
1. **What happened?** 运行"文档升版"脚本（PLAN→v19 / SCOPE→v3.7 / DECISIONS 追加 D-027 / DEV_LOG 追加日志）后，`docs/PLAN.md`、`docs/PROJECT_SCOPE.md`、`docs/DECISIONS.md`、`docs/DEV_LOG.md` **全部变成 4 字节**，内容只剩下字符串 `utf8`。而脚本输出不是"全失败"，而是**前几条显示成功、后面才开始报"锚点找不到"**。
2. **What did we first think was wrong?** 一开始以为是编码问题（BOM / CRLF / 全角冒号与中点字符差异）导致锚点匹配不上，甚至怀疑文档里的 `·`「｜」等字符与脚本不一致，准备逐个核对字符。
3. **What was the real cause?** 脚本里的写入封装写错了：`const write = (f, s) => fs.writeFileSync(D + '\\' + f, 'utf8')` —— **漏掉了 `, s`**。于是每次调用都把"编码字符串 `utf8`"当作**文件内容**写入。连锁反应解释了全部现象：第一个补丁"成功"→ 文件立刻被写成 4 字节 → 下一个补丁再去读，读到的就是 `utf8` → 任何锚点都匹配不上 → 报"命中 0 项"。**"前几条成功、后面全失败"其实是"文件正在被自己覆盖"的典型信号**，当时没有第一时间识别。
4. **How was it fixed?** ① 立刻停止继续执行脚本，先做损失盘点（`docs/` 目录逐文件列大小），确认只有这 4 个文件被破坏；② 找到尚未被破坏的镜像副本 `neurobase/public/docs/`（上一次 `npm run check` 成功同步的产物）与 `outputs/neurobase/dist/docs/`，确认 4 个文件都完好（23995 / 14403 / 17481 / 24461 字节，即 v18 / v3.6 状态），哈希比对一致；③ 从镜像恢复 `docs/` 下这 4 个文件；④ 重写脚本：**先在内存里完成全部替换并逐条断言命中次数，全部通过后才一次性写盘**，写入前后还校验"新内容非空、比原文长、写后回读能命中新标记"，任何一步不满足就整体放弃、绝不半途落盘；⑤ 重跑 `npm run check`，确认 13 个文档同步镜像正常、站点 `/docs/*` 可访问。
5. **What did I learn?** ① 批量改文件之前**先确认存在可用的备份或镜像副本**——本项目的 `public/docs` 同步镜像这次意外成了救命稻草；② 改文件应当**先在内存里算好、校验通过再落盘**，避免"改一半、又把这半改坏"的连锁破坏；③ 错误模式本身是重要线索：**"前半成功、后半全失败"往往不是匹配问题，而是目标文件已经被写坏了**，应立刻停下来看文件本身，而不是继续调锚点；④ 自己的工具函数（read/write 这种一次性封装）必须极简、并在第一次使用时就用"读回来的内容对不对"来自检。
### E-004 · 用 `-LiteralPath` 配通配符导致"复制静默未执行"，产物目录一度残缺（2026-10-10）
1. **What happened?** 刷新静态产物 `outputs/neurobase/dist/` 时，我执行了两步：先把 `neurobase/dist` 复制过去，再删除"源里已不存在"的陈旧哈希文件。脚本输出显示"已覆盖复制: 源 26 个文件"和"已删除 11 个陈旧文件"，看起来一切正常；但随后的复核报出 `产物: 15 个 / 259 KB`、`index-B3fzV2vf.css 等 11 个路径不存在` —— 产物目录里 **`index.html` 引用的 11 个 chunk 全部缺失**，站点产物等于打不开。
2. **What did we first think was wrong?** 第一反应是"源目录又重建了、哈希变了"：因为我在两次命令之间跑过 `npm run check`（含 `vite build`），哈希文件名确实整体变过一轮，很容易把"差异 11"解释成正常的版本更替。
3. **What was the real cause?** 复制那一步**根本没有发生**。我写的是 `Copy-Item -LiteralPath "$src\*" -Destination $dst -Recurse -Force` —— `-LiteralPath` **不做通配符展开**，`"$src\*"` 被当成一个字面路径；PowerShell 没有把它当作致命错误，脚本继续往下跑。于是：① 复制 = 空操作；② 我却**照常执行了删除**（删除集合是按"源 vs 产物"的相对比较算出来的，产物还是上上轮构建，于是删掉了仍需要的文件）；③ 那句"已覆盖复制: 源 26 个文件"是**我自己拼的字符串**，不是工具返回的结果，把失败伪装成了成功。本质上仍是 E-003 的同类错误：**破坏性操作前没有先验证前置步骤真的成功**。
4. **How was it fixed?** ① 先盘点两个目录的真实文件数与大小，确认产物是残缺状态、源构建完好（26 文件 / 706.8 KB）；② 改用 `robocopy $src $dst /MIR` 做**真正的镜像**（用户已确认允许清理该目录内的陈旧文件），robocopy 的 `/MIR` 会同时补齐缺失文件并清除多余文件；③ 镜像后逐项复核：文件数一致（26 = 26）、"仅源有 / 仅产物有"均为空、**逐文件 SHA256 全部一致**、总大小 706.8 KB、`docs/PLAN.md` 版本行为 `v22`；④ 确认 `index.html` 引用的 chunk 全部存在。
5. **What did I learn?** ① **`-LiteralPath` + 通配符 = 不发生任何事**：凡是要展开 `*` 的场景一律用 `-Path`；② 复制、删除这类破坏性操作必须拆成"复制 → **验证复制结果**（文件数 + 哈希）→ 清理 → 再验证"，绝不在未验证的前提下执行清理；③ **"脚本没报错" ≠ "操作成功"** —— 输出里那句是我自己 echo 的字符串，真正的证据只能来自 `Test-Path` / `Get-ChildItem` / `Get-FileHash`；④ 版本更替（哈希文件名变化）会掩盖问题，判断"陈旧文件"应当以**当前源目录的实际列表**为准，并在复制确认成功之后再算。

### E-005 · 缺少 matchMedia 的环境下整页脚本中断（首页白屏）（2026-10-11）
1. **What happened?** 原生版三页写完后用 jsdom 跑自动校验，首页在断言「模块卡数量」时一张都拿不到；调试脚本显示 `terms.js` / `i18n.js` / `core.js` 都执行成功，唯独 `page-home.js` 抛出 `TypeError: window.matchMedia is not a function`（调用链 `applyTheme` ← `mountShell` ← `page-home`），首页脚本就此中断，页面等于空壳。
2. **What did we first think was wrong?** 第一反应是「jsdom 测试环境太简陋、缺 API 属于测试环境问题」，打算只在测试脚本里补个桩糊过去。
3. **What was the real cause?** 桩确实是测试环境的事，但**代码本身也有真实缺陷**：`applyTheme()` 在判断「跟随系统」时直接调用 `window.matchMedia(...)`，没有任何保护。一旦运行环境不提供它（老内核、内嵌 WebView、部分受限浏览器），异常会从每页必跑的 `mountShell` 一路抛出，导致**整页脚本中断**——不是某个按钮失灵，而是直接白屏。更麻烦的是数据加载与渲染其实完全正常，反而更难怀疑到「主题」这个边角功能上。
4. **How was it fixed?** ① `core.js` 新增 `prefersDark()`：`window.matchMedia` 不存在或调用抛错时一律返回 `false`（主题退化为白天），让非核心功能绝不拖垮整页；② 三个页面的首屏内联脚本把「主题」与「字号」拆成**互不牵连的两个 `try`**，一边失败不再影响另一边；③ 校验脚本改为默认注入 matchMedia 桩（贴近真实浏览器），并**新增一条专门的回归用例**：把 matchMedia 拿掉后页面仍须渲染出 11 张模块卡且无脚本错误。
5. **What did I learn?** ① 「测试环境缺 API」不等于「代码没问题」——要分两步问：环境该不该有它？即便有，我的代码在它缺席时是否还站得住？② **每页必跑的初始化路径（`mountShell` 这类外壳）里不能有任何可能抛异常的调用**，能力探测要写在最靠近使用点的地方；③ 非核心功能（跟随系统主题）必须**优雅降级**，最坏只是不跟随系统，绝不能影响页面主体；④ 修完要把它变成一条断言（拿掉 matchMedia 仍能渲染），否则下次重构会静默复发。

### E-007 · 反馈箱校验逻辑缺陷 + jsdom 合成 submit 事件不可靠（2026-10-13）
1. **What happened?** 反馈箱冒烟测试两个现象：① 空内容（全空格）竟然提交成功 —— 类型校验 `if (!TYPE_IDS.indexOf(tVal) >= 0)` 恒为真（`indexOf` 命中返回 ≥0 时 `!≥0` 为 false，未命中返回 -1 时 `!-1` 为 false，两分支都不进，等于没有校验），且表单路径校验的是**未 trim 的原始值**，`'   '` 非空字符串直接通过；② jsdom 里对表单 `dispatchEvent(new Event('submit'))` 抛未捕获 `DOMException {}`，测试进程中断，无法验证「表单提交 → 写入 localStorage」链路。
2. **What did we first think was wrong?** 第一反应是"jsdom 不支持表单事件、换触发方式"，差点绕开问题只改测试。
3. **What was the real cause?** ① 校验函数同时被「表单路径」与「测试直呼」两种方式使用，但 trim 只发生在表单路径、校验只看原始值 —— **接口约定不统一**；且布尔表达式 `!A >= 0`（`(!A) >= 0`）与直觉的 `!(A >= 0)` 语义完全不同；② jsdom 对表单 `submit` 合成事件支持不完整，属环境限制，但更根本的问题是**测试只能通过合成事件触发，无法直呼提交逻辑** —— 提交逻辑没有暴露可复用的程序入口。
4. **How was it fixed?** ① 把提交拆为两个对外接口：`createRecord(tVal, bVal, otherVal)`（内部统一 `String(bVal).trim()`，空内容 / 超 1000 字返回 null 并提示）+ `saveRecord(rec)`；表单提交与测试共用同一入口，校验规则只有一个实现；② 类型校验改为 `TYPE_IDS.indexOf(tVal) < 0` 才回退 `other`；③ 冒烟 / 自测不再合成 `submit` 事件，改直呼 `createRecord + saveRecord`，并补「空内容被拒绝」「超长被拒绝」断言；④ 顺带把 `file://` 下 jsdom localStorage 不可写的问题解决（自测加载统一 `https://nb.local/`）。最终 311 项全绿。
5. **What did I learn?** ① **布尔表达式写错是静默的**：`!A >= 0` 这类「取反与比较混排」极易出错，校验一律写成直白比较（`indexOf(x) < 0`）；② **校验入口要唯一**：同一套校验规则被多个调用方使用时，必须收敛到同一个函数（trim / 边界检查放在函数内部），否则"表单通过、测试被拒"这类接口不一致会长期潜伏；③ 测试不应依赖"合成浏览器事件"来驱动业务逻辑 —— 业务提交必须有程序入口（`NB.feedback.createRecord / saveRecord`），事件只是它的 UI 触发器；④ 环境限制（jsdom 表单事件）要区分于产品缺陷，但**凡是测不动的链路，都要先怀疑"是不是代码没有可测接口"**。
### E-008 · 反馈箱 dialog 嵌套致弹窗不显示：遮罩出现、内容被内层 closed dialog 藏住（2026-10-13）
1. **What happened?** 人工验收反馈箱：点击导航「反馈箱」按钮后，页面出现半透明遮罩（`::backdrop`），但对话框本体完全不显示 —— 没有标题、表单、关闭按钮，只有遮罩盖住整页。截图可见「遮罩已挂载、弹窗内容缺失」，与"弹窗打开但内容渲染失败 / 层级错乱"的表现一致。

3. **What was the real cause?** `ensureDlg()` 先用 `document.createElement('dialog')` 创建外层 dialog（设 `id='nb-fb-dialog'`），再 `dlg.innerHTML = dialogHtml()`；而 `dialogHtml()` 返回的字符串**又自带一层 `<dialog class="fb-dialog" id="nb-fb-dialog">…</dialog>` 包裹** → 实际 DOM 是 dialog 套 dialog、两层**重复 id**。外层 `showModal()` 成功 → 遮罩出现；内层 dialog 未 open（规范样式 `display:none`）把 `.fb-card` 全部内容藏住。jsdom 不做真实布局渲染，内层 dialog 的隐藏不影响 DOM 查询（元素都在文档树里），因此 311 项全绿也抓不到 —— 只有真实浏览器可见。
4. **How was it fixed?** ① `dialogHtml()` 去掉自身 `<dialog>` 包裹，只返回 `.fb-card` 内部结构；② `ensureDlg()` 创建的外层 dialog 补 `aria-labelledby="nb-fb-title"`（无障碍引用保持）；③ 新增回归断言「dialog 内不嵌套 dialog」到 `verify-native.mjs`（`!dlg.querySelector('dialog')`），防止同类结构再出现；④ 全量 307 项全绿。
5. **What did I learn?** ① **"元素存在"的 DOM 断言抓不到"元素不可见"**：jsdom 的 `querySelector` 只能证明结构存在，`display:none` / 层级 / 嵌套隐藏这类渲染缺陷必须在真实布局引擎里看（或至少加"结构合法性"断言如"不嵌套同类宿主元素"）；② **宿主元素创建 + 模板字符串自带宿主标签 = 双重包裹陷阱**：`createElement('dialog')` 与 `<dialog>…</dialog>` 字符串二选一即可，两者同用必然嵌套；③ **重复 id 会掩盖错误**：两层同 id 的 dialog，外层被遮罩 / 选择器命中时容易误判"弹窗正常"，id 必须唯一、且断言应检查结构边界。

### E-011 · UTF-8 BOM 与 PowerShell 引号让中文内容「静默损坏」（2026-11-09）
1. **What happened?** 批量生成 / 合并中文 JSON 与 Markdown 时出现三类现象：① `JSON.parse` 在文件开头报 `Unexpected token`；② 中文变成 `?` 或乱码；③ 某些字段被截断，文件「看起来写成功了」但内容不完整。
2. **What did we first think was wrong?** 先怀疑 JSON 逗号 / 引号语法写错，又怀疑源数据本身编码有问题，逐个文件手工核对，耗时很久。
3. **What was the real cause?** 三个原因叠加：① PowerShell 5.1 默认按系统 ANSI（936）解析无 BOM 的 UTF-8 脚本，管道传给子进程时 `$OutputEncoding` 又是 ASCII，中文在传递过程中被替换成 `?`；② 写入时带了 UTF-8 BOM，而 `JSON.parse` **不接受 BOM 前缀**，于是「内容完全正确」的 JSON 依然解析失败；③ 通过命令行参数传含双引号的中文 JSON 片段时，引号被 shell 提前截断，只写入了前半段。
4. **How was it fixed?** ① 中文密集的读写改用 Node / Python 并显式指定 `utf-8`（Python 读取用 `utf-8-sig` 兼容 BOM，写 JSON 时不带 BOM）；② PowerShell 侧先设 `[Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)`；③ 中文与引号密集的内容改走**文件**而不是命令行参数；④ 每次生成后立刻回读：`JSON.parse` + 条目数 / 字段数比对，不通过就整体失败。
5. **What did I learn?** ① **「写成功」不等于「写对了」**：中文文件必须回读校验（解析 + 计数 + 抽样），不能只看写操作没报错；② **BOM 是 JSON 的隐形杀手**，也是「同一份文件在我的工具里正常、在浏览器里报错」的常见原因；③ 不要让 shell 参数承载中文与引号密集内容，shell 的编码与转义规则会成为不可见的中间层；④ 编码问题会伪装成「语法错误」，排查时应先验证**字节层面**（BOM / 编码 / 长度），再怀疑语法。

### E-020 · 空格键绑定「反应」会与聚焦按钮的原生 click 重复计数（2026-11-12）
1. **What happened?** 为简单反应时增加空格作答时，若焦点停在「反应」按钮上，一次 Space 可能同时触发 document 的 `keydown` 与浏览器合成的按钮 `click`；第二次会走 false start 分支，把「太早了」写进成绩行并重排本轮。
2. **What did we first think was wrong?** 起初认为 `e.repeat` 过滤加 `preventDefault()` 就足够，因为默认行为被阻止后不应再产生 click。
3. **What was the real cause?** Space 的按钮激活默认行为发生在 keyup 阶段，由浏览器合成 `click`；`keydown` 的 `preventDefault` 在各浏览器/焦点位置下并非都能完全抑制这条路径，而焦点不在按钮上时又只有 `keydown`。两条路径都必须去重，不能只依赖默认行为被阻止。

5. **What did I learn?** ① 把快捷键映射到可点击控件时，要假设「一次物理按键 = keydown + 可能的 click」；② 去重应放在业务入口（`rtAnswer`）而不是只靠事件层的 `preventDefault`；③ 去抖窗口要小于正常试次间隔、大于同一次按键的事件间隔（60ms 足够，试次间隔 ≥420ms）。

1. **What happened?** Phase 6 账号面板的「退出登录」按钮渲染出英文标识 `signOut`，而不是任何可读文案。代码写的是 `esc(T('signOut') || 'Sign out')`，看上去是有兜底的。
2. **What did we first think was wrong?** 先怀疑字典里键名拼错（`signout` / `logout`）、大小写不一致，或 `T()` 返回 `undefined` 使 `||` 生效但 fallback 又被别处覆盖。
3. **What was the real cause?** `core.js` 的 `t()` 在字典缺失时执行 `if (out == null || typeof out !== 'string') return key;`——**返回键名本身**。`'signOut'` 是非空字符串（truthy），所以 `|| 'Sign out'` 右侧永远不执行；页面上于是出现「看起来像变量名」的文案。这不是拼写错误，而是「缺键回退」与「truthy 兜底」两种机制互相抵消。
4. **How was it fixed?** 在 `auth-ui.js` 的 `TXT.zh / en` 补齐 `signOut`、`dataLabel` 两个键；新文案统一约定 `var v = t(k); if (v === k) v = fallback;`，不再用 `||`。`verify-native` 的 Phase 6 断言覆盖按钮与浮层的实际文案，`cloud-check` 覆盖配置留空与密钥扫描。
5. **What did I learn?** ① 「缺键返回 key」是便于定位的好设计，但它与 `value || default` 天然冲突；凡是用「返回自身作为占位」的 API（i18n、`getOption()`、`find()` 的哨兵），兜底必须显式比较 `v === key` / `v === sentinel`，不能靠 truthy；② 新增文案前先确认字典里是否真的有这个键，再决定要不要写兜底；③ 断言要覆盖「渲染出来的文字」，而不只是「元素存在」——这个 bug 在所有「元素存在」类断言下都是全绿的。

1. **What happened?** v1.23.8 已删掉 `left/top` 过渡、保留 `.is-dragging { transition: none }`，但用户仍反馈松手时球被甩向边缘。Edge headless 复现：拖动 `(380, -260)` 松手，`left` 从 `398` 突跳到 `778`，随后 0.22s 滑回 `398`。
2. **What did we first think was wrong?** 先怀疑落点算错（把 `dx` 加了两次）、`pointerup` 坐标异常，或者 `rememberFab` 存的比例把位置带偏。
3. **What was the real cause?** 落点计算是对的，问题在「提交顺序」：`finish` 里先 `pinFab` 把 `left` 增加 `dx`，再清空内联 `transform`、最后摘 `.is-dragging`。这三步在同一帧提交，浏览器判断是否过渡时用的是**变更前已提交的计算样式**——那一帧 `transition: transform 0.22s` 仍然有效，于是 `transform` 从 `translate3d(dx,dy)` 过渡到 `identity`；与此同时 `left` 已经 +`dx`，视觉位置 = 落点 + `dx`，位移被叠加成 `2dx`（大位移时正好被视口裁在边缘）。

5. **What did I learn?** ① CSS 过渡的开关不是看「当前帧 class 里写了什么」，而是看变更提交前浏览器已经算出的 `transition-*`；同一帧里加/摘 `transition: none` 再改位移，等于没锁。② 锁过渡必须「内联禁用 + 强制重排 + 分帧恢复」三件套。③ 叠加类 bug 要看**合成后的视觉位置**（`left + transform`），不能只验证最终 `left/top`；浏览器自动化读数 + 多个时间点采样（松手即刻 / 60ms / 460ms）能直接暴露中间态。

1. **What happened?** 浮球第一版改成「玻璃球 + 液体」后，浅色页面上的球像磨砂塑料：文字被模糊到几乎不可读，白色渐变把背景完全盖住；同时液体初始版本把 `animation` 放在承载物理 `transform` 的元素上，CSS 动画直接覆盖 JS 写入的倾斜角度，拖动时液面不动。

### E-035 · 速度差分的量纲陷阱：加速度小 1000 倍导致「只倾斜、不翻滚」（2026-11-19）
1. **What happened?** 液体物理升级后，快甩能倾斜（约 9°），但 `--liquid-spin` 恒为 0、水花几乎不出现；断言「快甩触发翻滚（spin > 3）」失败，而慢拖 / 快甩的倾斜量差异只有 6 倍左右，和设计的量级不符。
2. **What did we first think was wrong?** 先怀疑 CDP 采样间隔太大漏掉峰值、headless 把 rAF 节流、`spin` 的 clamp 设得太小，以及 `spinV` 的阻尼吃掉角动量。逐项排查后都不是：延长采样、加 `--disable-background-timer-throttling`、放大 clamp 都无效。
3. **What was the real cause?** 加速度量纲算错。`vx` 已经是 px/ms，`ax = (vx - pvx) / sec / 1000` 里再除 1000，使结果比真实值小 1000 倍：一次「1 px/ms 在 16ms 内突变」本应是 62.5 px/ms²，实际算出 0.0625。惯性项 `axS` 因此恒接近 0，倾角几乎全靠速度项，`spinV += axS * 105 * sec` 基本不增长，水花判据也一起失效。所有现象都由这一个量纲错误解释。
4. **How was it fixed?** 改用「归一化到 16ms 的速度增量」作为驱动量：`dv = (vx - pvx) * (0.016 / sec)`，clamp ±4，再低通成 `axS`。三个增益重新标定：`tiltTo = axS*6.5 + vx*4.2`、`spinV += axS*900*sec`、`slosh = |axS|/1.8 + |vx|/1.9`。修复后实测：慢拖 1.3° / slosh 0.06，快甩 8.7° / slosh 0.67 / spin 峰值 38°。
5. **What did I learn?** ① 物理量先写量纲、再写代码；「速度差再除以时间」是最容易差 1000 倍的写法，尤其当速度单位是 px/ms 而时间用秒。② 用「每帧速度增量」这类无量纲化的驱动量，天然免疫事件间隔抖动，比 `Δv/Δt` 更适合离散的鼠标事件。③ 断言要分通道：只断言「拖动了有倾斜」会漏掉「倾斜了但没翻滚 / 没水花」，每个物理通道都要有独立判据，才能在一个量纲错误下同时暴露问题。

### E-037 · 离散指针采样下用「加速度 × 速度 < 0」判断掉头，条件永不成立（2026-11-19）
1. **What happened?** 给上下甩动加水花时，用 `Math.abs(dvY) > 1.0 && dvY * vy < 0` 作为「掉头」判据。实测拖动中 `burst` 始终为 0，只有松手才溅水；`slosh` 却也拉到了 0.82，说明移动事件本身是通的。
2. **What did we first think was wrong?** 先怀疑 `dvY` 太小（归一化到 16ms 后被压到 0.75），于是把阈值从 1.0 降到 0.3 —— 仍然为 0，说明不是幅度问题。
3. **What was the real cause?** 指针事件是 38ms 一帧的离散采样：上一帧 `vy = -0.89`、这一帧 `vy = +0.89`，中间没有「减速到 0」的帧。于是 `dvY` 与当前 `vy` 同号（都在新方向上），`dvY * vy` 恒为正，判据永远不成立。真实世界里掉头是连续的减速—反向，离散采样里它只表现为**一次符号跳变**。
4. **How was it fixed?** 去掉方向乘积，改成「加速度幅度阈值 + 脉冲注入」：`if (Math.abs(dvY) > 0.45) burst += |dvY| * 0.8`。匀速拖动时 `dvY ≈ 0` 不触发，掉头与急停时 `dvY` 突增自然触发；实测 `burst` 峰值 0.60，松手 340ms 内归零。
5. **What did I learn?** ① 连续时间的物理判据（`a·v < 0`）不能直接搬到离散事件流上，要先问「这个信号在采样点上长什么样」。② 判断「方向反转」应直接比较前后两帧的速度符号（`vy * prevVy < 0`），或干脆用加速度幅度。③ 断言全 0 时，先看同一通道里「应该有值」的相邻变量（这里是 `slosh`）是否正常，能快速区分「没触发」与「没执行」。

### E-039 · 振荡系统不能用「固定时刻采样」判定已静止（2026-11-19）
1. **What happened?** 交互探针原本是「松手 → `sleep(900)` → 读一次 `--liquid-tilt`，要求 < 0.6°」。加大波幅后该断言失败，读到 1.27°；把等待改成 1100ms 反而更差（2.25°）。

### E-040 · Crossref 只给年月，补齐日期后把「精度差异」当成内容变更（2026-11-19）
1. **What happened?** Phase 7 第一次在线同步核对 13 个 DOI，报出 3 条变更：`tang-2023` 的 date 从 `2023-05-01` 变成 `2023-05`、`hochberg-2012` 从 `2012-05-16` 变成 `2012-05-01`，另一条是 Oxley 2020 标题补全。前两条每次重跑都会再次入队。

### E-042 · 面通量「边算边写」，浅水模型每帧悄悄漏掉一点水（2026-11-19）
1. **What happened?** 球内液体换成一维浅水后，静止和倾斜都正常，但长时间跑体积会缓慢下降：6 s 往复拖动后总水量少 15%，松手 4 s 少 4%。体积是这套模型的硬指标（半瓶水必须是半瓶），一眼就能看出问题。
2. **What did we first think was wrong?** 先怀疑干湿边界：`h<0` 被 clip 到 0 会吃掉水量。于是加了「把裁掉的量按剩余容量还回去」的局部质量修复，又把 `Float32Array` 换成 `Float64Array` 防精度丢失 —— **体积仍然掉**，而且 `lastOverflow` 一直是 0，说明根本没有发生过 clip。
3. **What was the real cause?** 通量在 `for (i...)` 循环里**边算边写**：处理第 i 列时先算左面 `faceFlux(i-1)`、右面 `faceFlux(i)`，紧接着写回 `h[i]`。下一个迭代再来算 `faceFlux(i)` 时，迎风格式读到的 `h[i]` 已经是新值 —— 同一个面在两侧被算成了两个不同的通量，界面上的水不再严格抵消。误差每步只有 1e-4 量级，跑上千步就累积成百分比。
4. **How was it fixed?** 改成两阶段：先把所有面通量算进 `Float64Array F[]`，再统一用 `F[i-1]` / `F[i]` 更新 `h[i]`。这样相邻两列共享同一个数，内部界面必然抵消，体积漂移立刻从 2.8% 变成 **0.00%**（`diag-vol` 实测最大单步损失 2.4e-15）。干湿裁断在正确写法下不再触发，质量修复降级为保险。
5. **What did I learn?** ① 有限体积 / 浅水这类格式的守恒性，靠的是**同一个面通量被两侧共用**，任何「先改状态再算下一个面」的写法都会破坏它，而且症状是缓慢、不易察觉的。② 守恒类 bug 先看**离散顺序**，再看精度：换 Float64 没用的那一刻，就该想到是算法顺序而不是舍入。③ 给模型加一条「体积必须守恒」的自动断言，比肉眼盯液面可靠得多 —— 这个 bug 在截图里完全看不出来。

### E-043 · 补丁脚本按 `\n` 匹配 CRLF 文件，锚点全部落空（2026-11-19）
1. **What happened?** 写脚本批量改 `verify-native.mjs`：按 `indexOf('  {\n    const htmlAll…')` 定位要替换的断言块，结果抛 `missing end`，脚本在写盘前退出，白跑一次。

### E-044 · 人工粘性扩散了水深 h，静止平衡态被破坏、6 s 漏掉 19% 的水（2026-11-19）
1. **What happened?** 为了压掉液面锯齿，在浅水每步末尾对水深 `h` 做一次 1-2-1 扩散并把总量差补回。静止与单向加速都看不出异常，但 `fluid-check` 第 8 项直接失败：6 s 往复拖动体积漂移 **−18.977%**。
2. **What did we first think was wrong?** 以为是 `clamp(h, 0, 2b)` 在贴顶干格处吃掉水量，准备把 clamp 掉的量再分配回去。
3. **What was the real cause?** 静止时 `h(x) = b(x) = √(1-x²)` 是**弧形底床**，不是常数。对 `h` 做拉普拉斯扩散，等于每一列都在把水从贴壁处往中心推 —— 平衡态本身被改掉了，水面持续流动，贴壁列反复被 clamp，水量就一步步流失。补回 `sum(h)` 的均值差救不了：它只保住总量，保不住「h 应该等于 b」这个形状。
4. **How was it fixed?** 改为扩散**自由表面 `s`**：静止时 `s ≡ 0` 是常数，扩散它才是对波形做低通、不触碰平衡态；扩散后由 `h = b - s` 反算水深，并把 `sum(s)` 补回不变 → 体积严格守恒。6 s 往复漂移回到 **−0.262%**，20 项全绿。
5. **What did I learn?** ① 在「变底床」模型里，`h` 和 `s` 不是同一个东西：`h` 的静止解是非平凡的 `b(x)`，任何「平滑 h」的直觉操作都会改变平衡态；要平滑的是**相对静水面的偏移**。② 守恒量断言（体积 / 总质量）是这类错误的唯一可靠哨兵 —— 肉眼完全看不出来。③ 扩散系数要按物理时间估（`ν = α·dx²/dt`）：2400 Hz 下每步一次、`α = 0.006` 已足以在几十步内抹平 2~4 格短波，同时让主波衰减时间保持在 5 s 量级；`α` 再大一点就会把真实波浪一起抹平。

### E-045 · 「静止」判定只看速度，水波过零时把倾斜的液面冻住（2026-11-19）
1. **What happened?** 用户反馈拖动晃动球后，液面回不到水平，会斜着卡一下。复现时发现：液面明显倾斜，但 `isCalm()` 连续 0.35 s 返回 true，rAF 停帧，液面就冻在当前角度。

2. **What did we first think was wrong?** 先怀疑 CSS 改动没生效、`?v=` 缓存指纹没换、静态服务读的是旧目录；又怀疑 headless 视口没真正设成 320，或 `.table-wrap` 的 `overflow-x:auto` 被别的规则覆盖。
3. **What was the real cause?** 两层错。① `scrollWidth` 统计的是元素**内容**宽度：`.table-wrap` 里的表格本身 623px，容器给的是横向滚动，不是页面溢出。② 判断「有没有越界元素」时用 `window.innerWidth` 作基准，而移动端布局视口会被内容撑开（320 → 490），于是真实超出 320 的元素落进 490 之内，被算作「没越界」——一个假阳性配一个假阴性，结论全错。
4. **How was it fixed?** 判据改为：把 `document.scrollingElement.scrollLeft` 设为 400，读回是否 > 0 —— 只有页面**真的能横向滚动**才算溢出；基准改用 `document.documentElement.clientWidth`。元素级只报 `getBoundingClientRect().right > clientWidth + 1` 且祖先里没有 `overflow-x:auto / scroll / hidden` 的节点，并排除 `skip-link` 这类 `left:-9999px` 的隐藏元素。改完后首轮仍报 130 个（说明这些是真溢出），修 CSS 后归零。
5. **What did I learn?** ① 「横向溢出」有两种：页面级滚动与容器内滚动，检测必须分开，`scrollWidth` 单独用会混为一谈；② 移动端 `window.innerWidth` 会被内容撑大，任何「视口宽度」基准都应取 `documentElement.clientWidth`；③ 一个「全部 0 问题」的检测脚本，必须先用故意越界的样例验证它抓得到，否则无法区分「真的没问题」和「脚本没生效」。

### E-059 · 导览高亮「永远差一段」：平滑滚动下读到了动画起始帧（2026-11-20）
1. **What happened?** 帮助导览打开后，高亮框总比目标元素偏上一段，越靠下的区块偏得越多；点「下一步」时框还会先停在旧位置再滑过去。
2. **What did we first think was wrong?** 以为是 `scrollIntoView({block:'center'})` 没生效、sticky 顶栏把元素挡住了，或者 `position: fixed` 的高亮框被某个祖先的 `transform` 改了包含块。
3. **What was the real cause?** 页面全局 `html { scroll-behavior: smooth }`。`scrollIntoView` 触发的是异步动画，紧接着调用 `getBoundingClientRect()` 拿到的是滚动**开始前**（或第一帧）的坐标；滚动距离越大偏差越大。第二个原因是窄屏下桌面导航与窄屏导航各渲染一份 `#nb-fb-open` / `#nb-help-open`，`querySelector` 取到的是 `display:none` 的桌面副本，高亮框直接变成 0 尺寸。
4. **How was it fixed?** 滚动前把 `html.style.scrollBehavior` 临时设为 `auto`，滚动后恢复；测量放进 `requestAnimationFrame` 并保留 700ms 逐帧校准，兜住字体替换 / 图片解码带来的二次重排；改用 `querySelectorAll` 遍历同名节点取第一个有尺寸的；用 Edge + CDP 逐步比较 `spot - target`，确认 1440 宽 8 步、390 宽 7 步偏差都是 0。
5. **What did I learn?** ① 任何「滚动后立刻测量」的代码都要先确认滚动是同步还是动画，`scroll-behavior` 是容易被忽略的全局隐式状态；② 视觉误差要用像素级探针（rect 相减）验证，肉眼「差不多」不可靠；③ 定位类功能必须同时处理「目标比可视区高」「目标贴边」「顶栏常驻」「重复 ID」四种边界，否则主路径修好了仍会在边界翻车。

### E-061 · 用 PowerShell 内联 Python 写 PDF 元数据，中文被写成乱码（2026-11-20）
1. **What happened?** 报告 PDF 导出正常，但写好元数据后回读，标题变成 `NeuroBase ??Ŀ???? ?? ...`，作者里的「王童」也成了问号；正文与文件名都没有问题。
2. **What did we first think was wrong?** 先怀疑 PyMuPDF 不支持中文元数据、PDF 只接受 Latin-1，或者阅读器解码问题。
3. **What was the real cause?** 元数据不是从文件读的，而是通过 `python -c "..."` 的**命令行参数**传入的。Windows PowerShell 5.1 在把参数交给 python 时按系统 ANSI（936）编码，Python 3 再按 UTF-8 解释，中文字节被替换成 `?` 后才进入 `set_metadata`。同一段代码写进 UTF-8 文件再执行就正常。
4. **How was it fixed?** 把写元数据的逻辑落到 `.deepworks/tmp/report-work/meta.py`（UTF-8 无 BOM）再执行；同时把标题 / 作者收敛为 ASCII（`NeuroBase - Project Report (V5.0.0)`、`Wang Tong`），彻底规避编码依赖；导出后用 PyMuPDF 回读，把五个字段写进 `meta-check.txt` 人工确认。
5. **What did I learn?** ① 中文不要走 shell 参数，尤其是嵌套一层解释器时；② 「工具支持中文」不等于「传递链路支持中文」，编码问题会伪装成库的缺陷；③ 交付类文件要有回读校验——写成功、页面能打开，都不代表内容正确。
